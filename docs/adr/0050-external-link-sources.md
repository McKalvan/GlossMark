# ADR 0050: Link sources outside the binary

Status: accepted, 2026-11-01. Refs issue #288 (step B of #209, the plugin SDK); follows [ADR 0049](0049-links-inferred-from-specs.md) (the `Source` interface, step A), [ADR 0021](0021-suggest-conf-is-measured-precision.md) and [ADR 0024](0024-auto-accept-precision.md).

## Context

[ADR 0049](0049-links-inferred-from-specs.md) put spec inference behind `infer.Source`: a source indexes its files once per run, declares the anchorable items of a spec file and the hints a code declaration names through the spec, and the suggest runner does everything else. AsyncAPI and OpenAPI are built in. The list of formats never ends (GraphQL, Protobuf, Avro, Terraform providers, in-house registries), and `gloss` is one static binary with a stdlib-first constraint, so Go's `plugin` package is out (#209). The v1.0 gate asks for an "outside plugin": something built outside this module, not compiled into `gloss`, that contributes to its output and is gated like everything else.

## Decision

1. **A plugin is an executable speaking versioned JSON over stdin and stdout.** The mechanism #209 proposes, applied to the first extension point. One process per source and per `gloss suggest` run; one JSON object per line; a single envelope (`type` plus the fields the type uses). The shapes on the wire are the `infer` package's own (`Concept`, `File`, `Item`, `Target`, `Decl`, `Hint`), so the protocol mirrors the interface call for call: `index` carries what `Index` receives (the files with their boundary directory and test flag, the vocabulary's concepts); `indexed` returns `Name`, every file's `Items` and the declared priors; `hints` carries one `Decl` and returns its `Hints`. The vocabulary's two lookups (`Named`, `CommonAncestor`) and file content are questions the plugin may ask back (`named`, `ancestor`, `read`), so a plugin can resolve a concept the way the built-in AsyncAPI source does, or just pass names to the matcher. `internal/infer/wire` holds the types, the client (`Client` is an `infer.Source`) and the server (`Serve` runs any `infer.Source` as a plugin). `Source.Index` now takes `infer.Files` instead of `*load.Workspace`, so what a source sees is exactly what the wire carries.
2. **Discovery: `PATH` and `glossmark.yaml`.** An executable named `gloss-source-<name>` on `PATH`, or a `sources:` entry (`name`, `command`) in `glossmark.yaml`, which wins for the same name and is the way to pass arguments or run an interpreter. A plugin named like a built-in replaces it; the core sources (`code`, `route`, `topic`, `schema`) cannot be taken. `gloss source list` shows the resolution. Discovery happens inside `suggest.Run`, so the calibration harness (`--calibrate`), `--eval` and the MCP path all see the same sources; `--calibrate` runs plugins from the original root, not its stripped copy.
3. **Contract handshake.** `index` carries `contract: 1` and the plugin answers with its own. A mismatch fails the command with a message naming both versions and the plugin (#209's requirement): a plugin written for a later contract never yields a half-understood graph. `gloss source serve` and the reference plugin answer a mismatched `index` with their own version first, so the failure is symmetric.
4. **A plugin's failure is a warning, not a stop.** A crash, output that is not the protocol, an answer under another name, a bad line range or a prior outside (0, 1] is reported once, as a GM700 warning naming the plugin, its command and where it was found, with the last lines of its stderr, and its proposals are left out; the other sources run. Only the contract mismatch is fatal, because it is the one failure that means the user's setup is inconsistent rather than one plugin being broken.
5. **Core keeps everything after hints.** Matcher resolution of `names` under `kinds` with each boundary's allowed set, conf from `<name>/<basis>/<role>`, the tie rule, dedupe against inline markers and manifest `links:`, anchoring (`scope=block` on an item's block, `scope=line` on a one-line item, which GraphQL fields are), flow direction from the code, marker rendering, the ledger's rejected links. Plugin output is proposals only. The one runner change beside discovery: a file in a language suggest does not read becomes a spec file when a source declares items in it (a `.graphql` schema, given a comment style), so a plugin can anchor on its own format.
6. **Calibration: namespaced bases, measured or capped.** A plugin's bases live under its name, as every source's do (ADR 0049 §6), so they never borrow another source's numbers and the shipped table cannot have measured them. Their conf reads, in order: the repository's own calibration when it measured the basis's row (`gloss suggest --calibrate --write` runs the plugins and writes their counts beside the rest, and from then on a plugin basis auto-accepts when its measured precision clears the target, like any other); else the prior the plugin declared, capped one hundredth below the auto-accept threshold in force (`Options.AutoAcceptThreshold`, the rule `gloss suggest` derived); else `calib.Unmeasured`. This implements the cap ADR 0049 §7 left for step B: a prior ranks proposals for the reviewer and never auto-accepts, only measured precision does (ADR 0024). A plugin that replaces a built-in inherits the built-in's shipped measurement, which is what makes the byte-identical proof meaningful.
7. **Proof of completeness.** `gloss source serve asyncapi` runs the built-in AsyncAPI source through `wire.Serve`; `TestExternalAsyncAPIIsByteIdentical` runs `gloss suggest` on a marker-stripped copy of claims-events with the built-in in process and again with `sources: [{name: asyncapi, command: [...serve asyncapi]}]`, and requires the proposals and the patch to be identical bytes. The interface has nothing the wire lacks.
8. **Reference plugin.** `examples/plugins/gloss-source-graphql`, a Go module of its own under this repository but outside the `gloss` module, with no dependency and no import from `internal/`: it defines its own copy of the wire shapes, as a plugin in another language would. GraphQL object types `represents` the entity they are named for; `Query`, `Mutation` and `Subscription` fields `documents` the process (for a query, or the entity) they name; code that defines or resolves a field `implements` it. It names no concept itself: names and kinds go to the matcher. It lives here rather than in glossmark-examples so its tests run with the protocol they test and a change to the contract changes both in one PR; the examples repository can carry a built copy.

## Consequences

- A team adds a format without a change to `gloss`: one executable, in any language, on `PATH`. Its proposals appear in `gloss suggest` under its own source, in `--eval` and `--calibrate` per source, and are reviewed, accepted and gated like every other proposal.
- A plugin cannot raise a link to accepted, cannot write the graph, cannot see the matcher's internals, and cannot auto-accept until the repository measures it. The worst a broken plugin does is a GM700 line and missing proposals.
- `docs/PLUGINS.md` is the authoring page and holds the contract; a change to the envelope that an old plugin would misread bumps `wire.Contract`, and the handshake turns the mismatch into a clear failure.
- Not done here: the other extension points #209 names (vocabulary importers, graph contributors) and a timeout on a plugin that hangs mid-run (the five-second grace applies only at close). Both fit the same mechanism.
