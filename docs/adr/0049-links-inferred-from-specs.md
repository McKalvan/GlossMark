# ADR 0049: Links inferred from the specs a repository already has

Status: accepted, 2026-10-28; revised 2026-10-31 to put the sources behind an interface (step A of #209). Refs issue #260; related to #65 (the suggest precision gate), #206 (tree-sitter anchoring), #208 (the SCIP join) and #209 (external sources). Follows [ADR 0021](0021-suggest-conf-is-measured-precision.md) and [ADR 0022](0022-what-suggest-proposes.md).

## Context

Teams already describe much of their domain in machine-readable form: an AsyncAPI contract names the events on every channel, an OpenAPI spec the operations and schemas of an API, a Strimzi `KafkaTopic` the topic it stands up, a migration or an ORM model the table an entity lives in. `gloss suggest` read none of them. Its evidence was the declaration's name, a concept doc that names it, its docstring, the tables its body touches and the code a test calls ([ADR 0022](0022-what-suggest-proposes.md)); a listener's topic literal was matched against event names word by word, which `claims.filed.v1` never matches. So a team with a contract restated it in markers, and the flows that drift checks (`publishes`, `subscribes`) were the ones suggest proposed worst: on claims-events it recalled 24 % of the labels and none of the flows.

The issue asks that inferred links carry a confidence, go through the same calibration as every other proposal, and become SOFT above the auto-accept precision, so that markers become the exception that corrects a wrong inference. Spec inference also sits at the edge between GlossMark and other stacks: every format is somebody else's, and the list never ends (GraphQL, Protobuf services, Helm topic lists, Terraform modules). So the first version must not hard-wire AsyncAPI and OpenAPI into the suggest runner; it must leave a seam an external tool can later fill (#209).

## Decision

1. **A `Source` interface, in `internal/infer`.** A source reads its files once per run and answers in plain data; it never sees the matcher or the graph, only a read-only `Vocabulary`:

   ```go
   type Source interface {
       Name() string                               // Proposal.Source, --source, and the namespace of its calibration bases
       Index(files Files, v Vocabulary) error      // the scanned files, each with its boundary directory and test flag (ADR 0050 made this a value, so the wire carries exactly it)
       Items(path string) []Item                   // what a spec file declares that a marker can anchor on
       Hints(d Decl) []Hint                        // what a code declaration names through the spec
   }
   type Vocabulary interface {
       Concepts() []Concept
       Named(name string, kinds ...string) []Concept   // exact name or alias, the matcher's tokenization
       CommonAncestor(curies []string) string          // nearest common is-a ancestor
   }
   ```

   An `Item` is a YAML block (symbol, role, lines, indent, doc) with the relation a marker on it means and a `Target`; a `Hint` is a `Target` with a fixed relation, or a flow: the channel the declaration names, the message on it when the code tells them apart, what named it and on which line. A `Target` is either a concept the source resolved through the vocabulary (`Concept`) or names and a doc for the runner's matcher (`Names`, restricted to `Kinds`, an implementation concept that realizes one of them counting), plus the evidence `Basis` for the calibration bucket and the `Terms` the reviewer sees. Every type is a value with JSON tags and no pointer into the binary, so a source outside it can return the same shapes (step B, #209). The runner is generic: it indexes the registered sources, asks each for a file's items and a declaration's hints, resolves targets through the matcher, chooses as it chooses any hit, reads conf from `source/basis/role`, dedupes, anchors and renders. The built-in sources are `asyncapi` and `openapi` (`infer.Builtin()`); a JSON spec is indexed, not proposed on (JSON carries no markers, ADR 0022).
2. **AsyncAPI.** The source resolves each channel to one event concept: the nearest common ancestor under `is-a` of the concepts its messages name exactly (name or alias), else the event the channel's key or address names. `claims.filed.v1` carries `MotorClaimFiled`, `FloodClaimFiled` and `FireClaimFiled`, so it stands for `ClaimFiled`; `payouts.v1` carries `PayoutAuthorized` and `PayoutFailed`, so `PayoutEvent`. The spec file gets one `documents scope=block` item per channel (basis `asyncapi/messages/channel`, or `asyncapi/name/channel` when the name decided). For a function or method the source returns a flow hint per channel it names: through its address, through an identifier the boundary binds to it (`filed_topic: str = "claims.filed.v1"`, `const val FILED_TOPIC = ...`, `filedTopic = "..."` in HOCON, `topic: payouts.v1` in YAML, a tuple of message names), or through a message name (`"ClaimWithdrawn"`, `MotorClaimFiled.newBuilder()`, `com.tidewater.claims.events.PayoutAuthorized`). A hint names a message when the code does (one proposal per message), else the channel (one for its concept); the source never says which way the flow goes. A flow is a proposal of its own beside whatever the declaration implements, so a declaration can carry several (`subscribes A`, `subscribes B`), as hand-written markers do (basis `asyncapi/flow/member`, `asyncapi/flow/func`).
3. **Direction is code analysis, in the runner.** Whether a declaration publishes to a channel or subscribes to it is a fact about the code, the same whatever spec named the channel, so it lives in `internal/suggest/flows.go` and no source decides it. A line that sends (`.send(`, `.to(`, `.produce(`, `.publish(`, `ProducerRecord(`) publishes what it names; a line that reads (`.stream(`, `.subscribe(`, `.poll(`, `.ReadMessage(`, a listener annotation) subscribes. A line that does neither takes the declaration's direction: what its name says (`publish*`, `send*`, `emit*`; `handle*`, `consume*`, `on*`, `process*`), else what its own calls do. A declaration with no direction gets no flow: a rule that compares `event_type == "FloodClaimFiled"` names the event for another reason. When one declaration of a file tells a channel's messages apart and another only names the channel in the same direction, the second is plumbing (`subscribe([filed_topic, ...])` opens the subscription that `handle(record_name)` serves) and is dropped.
4. **OpenAPI.** The source hands the runner names, not concepts: an operation item carries its `operationId` and path words with the summary as doc, restricted to processes and capabilities (or the mechanisms that realize one), and gets `documents scope=block` (basis `openapi/<evidence>/operation`, the matcher's evidence kind deciding between a process and the mechanism named after it); a schema item carries its name, restricted to entities, events and measures, and gets `represents scope=block` (`openapi/<evidence>/schema`). A handler whose decorators or body declare a route the document covers (same method, a document path that is or ends with the route's path, parameters normalised) gets a hint with the operation's names and a fixed `implements` (`openapi/<evidence>/func`). A route with no spec behind it stays core evidence: its path words, restricted to process-like concepts (`route/func`).
5. **Topics and tables stay in the runner.** They are one regex and one name match each, next to the resource and table matching the runner already does, and making them sources would add two `Index` passes for no interface gain. A Strimzi `KafkaTopic` is a resource declaration named `KafkaTopic/<topicName>`; it `provisions` the resource concept whose distinguishing words (`topic`, `queue`, `stream`, `kafka` and the like set aside) are all in the topic's name (`claims.filed.v1`: `FiledTopic`; basis `topic/resource`). A type that maps itself to a table (`__tablename__`, `@Table(name = ...)`, `tableName`, `db_table`, `@@map`) `represents` the entity a `represents` link already binds the table to, else the entity the table is named for (`schema/type`).
6. **Sources, measured apart.** Every proposal names its source: `code` (what suggest read before), `route`, `topic`, `schema` (tables, views, Prisma models and ORM mappings), and the name of each `infer.Source`. `gloss suggest --source a,b` keeps only those; `gloss suggest --eval` and `--calibrate` print precision, recall and the auto-accepted share per source beside the band and basis tables. A source's bases are namespaced under its name (`asyncapi/flow/member`), so `calib.Table` falls back from the basis to the source's evidence row (`asyncapi/flow/*`) and then to the source row (`asyncapi/*`), never to another source's numbers. Each is a row of the calibration table like any other, so an inferred link's conf is the precision its source measured ([ADR 0021](0021-suggest-conf-is-measured-precision.md)), and the auto-accept threshold treats it as it treats a name match ([ADR 0024](0024-auto-accept-precision.md)).
7. **An unmeasured source never auto-accepts.** A source the calibration set has not seen gets `calib.Unmeasured` (0.3) for every basis, which sits at the floor and below any threshold the default target derives. A future external source may declare a prior for its bases, as a hint to the reviewer, but the prior is capped below the auto-accept threshold in force: only precision measured on labelled links auto-accepts (the rule of ADR 0024, applied to sources). The cap is not implemented here, because nothing yet declares a prior; it is the contract step B must keep ([ADR 0050](0050-external-link-sources.md) implements it).
8. **What stays by hand.** `consumes`, `produces` and `holds` are not inferred from a spec: a schema in a request body says what an operation takes, not what the process consumes, and `holds` is declared ownership ([ADR 0037](0037-holds-is-declared-ownership.md)). Test names and test call graphs (`verifies`) already go through `calls/test`; test files are not read for bindings, because they bind fixtures, not the service's topics.

## Measured on the calibration set (2026-10-28)

Pooled, in sample, 1055 proposals at `--min-conf 0.01` against 883 labels; the default target 0.9 derives `conf >= 0.77`:

| source | proposals | correct | precision | labels recalled | auto-accepted | auto precision |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| asyncapi | 20 | 16 | 80.0 % | 16 | 16 | 87.5 % |
| topic | 6 | 6 | 100 % | 6 | 6 | 100 % |
| schema | 45 | 41 | 91.1 % | 41 | 34 | 100 % |
| route | 5 | 0 | 0 % | 0 | 0 | - |
| code | 979 | 255 | 26.0 % | 235 | 33 | 87.9 % |

claims-events, the one set with a contract: recall rose from 23 of 95 labels (24.2 %) to 38 (40.0 %); the AsyncAPI source made 20 proposals, 16 correct and 3 near (the publisher names the channel and the labels name its three messages; the consumer names `PayoutFailed`, which the label leaves out because the code only logs it). On a copy stripped of its markers, accepting the `asyncapi` and `topic` proposals alone closes every `publishes` and `subscribes` gap drift reported, and drift agrees with the marker version on the flows but for two findings the contract cannot know: the `ClaimReferred` violation (the referrals topic is in a Strimzi resource and in no channel of the contract) and the `PayoutFailed` gap (the marker version leaves the stub unlinked). The only OpenAPI spec in the set is the test fixture; `route` evidence, with no spec behind it, was wrong five times out of five and sits below the floor. The pooled held-out estimate moved from 10.6 % auto-accepted at 92.3 % to 11.6 % at 91.1 %.

## Consequences

- A repository with an AsyncAPI contract gets its flows from the contract. The markers to write are the ones that correct it: the publisher that names only the channel when the ontology wants the message, the consumer that handles an event the contract says it only logs.
- A spec item is anchored as a YAML block (`scope=block` above the channel, operation or schema key), as the hand-written markers in claims-events are.
- The calibration table carries the sources' bases under their names; `TestCalibrationTableIsFitted` refits them as the set grows, as for every other basis. `route` is kept as a measured basis so a repository that labels its handlers can find out whether its own routes carry more.
- Adding a format is a `Source` in `internal/infer` and nothing in the runner: `Items` for what its files declare, `Hints` for what code names through it, flows left to the runner. Step B (#209) is the same interface over a wire: an executable that is given the vocabulary and the declarations as JSON and returns items and hints as JSON, registered beside the built-ins and calibrated by its name. Its contract is what this ADR fixes: no direction, no relation the code has to settle, bases under its name, and no auto-accept until measured.
- Not done here: Kafka topic declarations outside Strimzi (a `topics:` list in a Helm values file, Terraform `kafka_topic` goes through the resource matcher as before), AsyncAPI operations' consumer groups as direction evidence (read and dropped: it marked every function in a consuming boundary that named an event), GraphQL schemas, and the `verifies` inference from test names beyond what `calls/test` does.
