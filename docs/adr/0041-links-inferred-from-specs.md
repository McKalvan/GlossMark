# ADR 0041: Links inferred from the specs a repository already has

Status: accepted, 2026-10-28. Refs issue #260; related to #65 (the suggest precision gate), #206 (tree-sitter anchoring) and #208 (the SCIP join). Follows [ADR 0021](0021-suggest-conf-is-measured-precision.md) and [ADR 0022](0022-what-suggest-proposes.md).

## Context

Teams already describe much of their domain in machine-readable form: an AsyncAPI contract names the events on every channel, an OpenAPI spec the operations and schemas of an API, a Strimzi `KafkaTopic` the topic it stands up, a migration or an ORM model the table an entity lives in. `gloss suggest` read none of them. Its evidence was the declaration's name, a concept doc that names it, its docstring, the tables its body touches and the code a test calls ([ADR 0022](0022-what-suggest-proposes.md)); a listener's topic literal was matched against event names word by word, which `claims.filed.v1` never matches. So a team with a contract restated it in markers, and the flows that drift checks (`publishes`, `subscribes`) were the ones suggest proposed worst: on claims-events it recalled 24 % of the labels and none of the flows.

The issue asks that inferred links carry a confidence, go through the same calibration as every other proposal, and become SOFT above the auto-accept precision, so that markers become the exception that corrects a wrong inference.

## Decision

1. **A spec index, built once per run.** `internal/suggest/spec.go` reads every YAML or JSON file whose head declares `asyncapi:` or `openapi:` (`swagger:`), and every Kubernetes document of kind `KafkaTopic`. A JSON spec is indexed, not proposed on (JSON carries no markers, ADR 0022).
2. **AsyncAPI.** Each channel is resolved to one event concept: the nearest common ancestor under `is-a` of the concepts its messages name exactly (name or alias), else the event the channel's key or address names. `claims.filed.v1` carries `MotorClaimFiled`, `FloodClaimFiled` and `FireClaimFiled`, so it stands for `ClaimFiled`; `payouts.v1` carries `PayoutAuthorized` and `PayoutFailed`, so `PayoutEvent`. The spec file gets one `documents scope=block` proposal per channel (basis `asyncapi/channel`). Code gets `publishes` or `subscribes` on a function or method that names a channel: through its address, through an identifier the boundary binds to it (`filed_topic: str = "claims.filed.v1"`, `const val FILED_TOPIC = ...`, `filedTopic = "..."` in HOCON, `topic: payouts.v1` in YAML, a tuple of message names), or through a message name (`"ClaimWithdrawn"`, `MotorClaimFiled.newBuilder()`, `com.tidewater.claims.events.PayoutAuthorized`). Where the code names messages on a channel, it gets one proposal per message; where it names only the channel, one for the channel's concept. A flow is a proposal of its own beside whatever the declaration implements, so a declaration can carry several (`subscribes A`, `subscribes B`), as hand-written markers do.
3. **Direction.** A line that sends (`.send(`, `.to(`, `.produce(`, `.publish(`, `ProducerRecord(`) publishes what it names; a line that reads (`.stream(`, `.subscribe(`, `.poll(`, `.ReadMessage(`, a listener annotation) subscribes. A line that does neither takes the declaration's direction: what its name says (`publish*`, `send*`, `emit*`; `handle*`, `consume*`, `on*`, `process*`), else what its own calls do. A declaration with no direction gets no flow: a rule that compares `event_type == "FloodClaimFiled"` names the event for another reason. When one declaration of a file tells a channel's messages apart and another only names the channel in the same direction, the second is plumbing (`subscribe([filed_topic, ...])` opens the subscription that `handle(record_name)` serves) and is dropped.
4. **OpenAPI.** Each operation is resolved to the process or capability (or the implementation concept that realizes one) its `operationId`, path words and summary name most strongly; the spec file gets `documents scope=block` on it (basis `<evidence>/operation`), and `represents scope=block` on a schema named for an entity, event or measure (`<evidence>/schema`). A handler whose decorators or body declare a route the spec covers (same method, a spec path that is or ends with the route's path, parameters normalised) gets `implements` on the operation's concept (`openapi/func`). A route with no spec behind it is name evidence on its path words, restricted to process-like concepts (`route/func`).
5. **Topics and tables.** A Strimzi `KafkaTopic` is a resource declaration named `KafkaTopic/<topicName>`; it `provisions` the resource concept whose distinguishing words (`topic`, `queue`, `stream`, `kafka` and the like set aside) are all in the topic's name (`claims.filed.v1`: `FiledTopic`; basis `topic/resource`). A type that maps itself to a table (`__tablename__`, `@Table(name = ...)`, `tableName`, `db_table`, `@@map`) `represents` the entity a `represents` link already binds the table to, else the entity the table is named for (`schema/type`).
6. **Sources, measured apart.** Every proposal names its source: `code` (what suggest read before), `asyncapi`, `openapi`, `route`, `topic`, `schema` (tables, views, Prisma models and ORM mappings). `gloss suggest --source a,b` keeps only those; `gloss suggest --eval` and `--calibrate` print precision, recall and the auto-accepted share per source beside the band and basis tables. Each new basis is a row of the calibration table like any other, so an inferred link's conf is the precision its source measured ([ADR 0021](0021-suggest-conf-is-measured-precision.md)), and the auto-accept threshold treats it as it treats a name match ([ADR 0024](0024-auto-accept-precision.md)).
7. **What stays by hand.** `consumes`, `produces` and `holds` are not inferred from a spec: a schema in a request body says what an operation takes, not what the process consumes, and `holds` is declared ownership ([ADR 0037](0037-holds-is-declared-ownership.md)). Test names and test call graphs (`verifies`) already go through `calls/test`; test files are not read for bindings, because they bind fixtures, not the service's topics.

## Measured on the calibration set (2026-10-28)

Pooled, in sample, 1055 proposals at `--min-conf 0.01` against 883 labels; the default target 0.9 derives `conf >= 0.77`:

| source | proposals | correct | precision | labels recalled | auto-accepted | auto precision |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| asyncapi | 20 | 16 | 80.0 % | 16 | 16 | 87.5 % |
| topic | 6 | 6 | 100 % | 6 | 6 | 100 % |
| schema | 45 | 41 | 91.1 % | 41 | 34 | 100 % |
| route | 5 | 0 | 0 % | 0 | 0 | - |
| code | 979 | 255 | 26.0 % | 235 | 33 | 87.9 % |

claims-events, the one set with a contract: recall rose from 23 of 95 labels (24.2 %) to 38 (40.0 %); the AsyncAPI source made 20 proposals, 16 correct and 3 near (the publisher names the channel and the labels name its three messages; the consumer names `PayoutFailed`, which the label leaves out because the code only logs it). On a copy stripped of its markers, accepting the `asyncapi` and `topic` proposals alone closes every `publishes` and `subscribes` gap drift reported, and drift agrees with the marker version on the flows but for two findings the contract cannot know: the `ClaimReferred` violation (the referrals topic is in a Strimzi resource and in no channel of the contract) and the `PayoutFailed` gap (the marker version leaves the stub unlinked). The only OpenAPI spec in the set is the test fixture; `route` evidence, with no spec behind it, was wrong five times out of five and sits below the floor. The pooled held-out estimate moved from 10.6 % auto-accepted at 92.3 % to 11.6 % at 91.1 %.

## Consequences

- A repository with an AsyncAPI contract gets its flows from the contract. The markers to write are the ones that correct it: the publisher that names only the channel when the ontology wants the message, the consumer that handles an event the contract says it only logs.
- A spec item is anchored as a YAML block (`scope=block` above the channel, operation or schema key), as the hand-written markers in claims-events are.
- The calibration table carries the sources' bases; `TestCalibrationTableIsFitted` refits them as the set grows, as for every other basis. `route` is kept as a measured basis so a repository that labels its handlers can find out whether its own routes carry more.
- Not done here: Kafka topic declarations outside Strimzi (a `topics:` list in a Helm values file, Terraform `kafka_topic` goes through the resource matcher as before), AsyncAPI operations' consumer groups as direction evidence (read and dropped: it marked every function in a consuming boundary that named an event), GraphQL schemas, and the `verifies` inference from test names beyond what `calls/test` does.
