# File formats

Three file kinds carry the ontology: the repository file, ontology files per namespace, and per-directory boundary manifests. Views are a fourth, optional file. JSON Schemas for all of them live in `schemas/`; the Go types in `internal/model` are the source of truth.

## `glossmark.yaml` (repository root)

```yaml
grammar: 1                                      # @gloss grammar version this repo is written in (default 1)
relations: starter                              # starter (what gloss init writes) | full; unset means full
owns:
  lib:  { iri: https://onto.acme.dev/library/,     file: ontology/lib.gloss.yaml,  tier: core,           version: 1.0.0, owner: library-services }
  circ: { iri: https://onto.acme.dev/circulation/, file: ontology/circ.gloss.yaml, tier: implementation, version: 0.3.0 }
imports:
  acq: { iri: https://onto.acme.dev/acquisitions/, version: "^2.1", source: ../acquisitions/ontology/ }
repo-iri: https://arch.acme.dev/circulation/    # an undeclared boundary prefix p: expands to <repo-iri>boundaries/p/
prefixes:
  acme: https://arch.acme.dev/boundaries/      # non-ontology prefixes (boundaries); optional with repo-iri
views: ontology/views.yaml                      # default
adoption: 3                                     # rung of the adoption ladder (QUICKSTART.md): 0 nothing fails, 1 check errors only, 2 drift and gate on critical/high concepts, 3 everything (default)
exclude: ["vendor/**"]
comment-styles: { ".pkl": ["//"], crontab: ["#"], "**/cron.d/*": ["#"] }   # extend the comment table
test-paths: ["**/tests/**", "**/*_test.go"]     # inferrer: implements in a test path also verifies
suggest:                                        # gloss suggest's defaults for this repository; flags override them
  auto-accept-precision: 0.9                    # SOFT = proposals whose evidence measured at least this precision (default 0.9)
  min-conf: 0.3                                 # lowest conf that becomes a proposal (default 0.3)
  stopwords: [widget]                           # words that never match a concept on their own (added to handler, manager, ...)
  labels: labels.tsv                            # what gloss suggest --calibrate scores against (default: the repository's own links)
  calibration: glossmark.calibration.tsv        # the repository's measurement, written by gloss suggest --calibrate --write
history:                                        # gloss history's defaults; flags override them
  step: commit                                  # commit (default) | first-parent | version
source-url: https://github.com/acme/circulation/blob/main/{path}#L{line}   # viewer links paths to the code host; gloss view --source-url overrides it; vscode opens paths in VS Code (embeds the local repository path); unset, paths are not links
policy:
  # soft-conf-threshold: 0.7                    # a fixed SOFT threshold; only when suggest.auto-accept-precision is not set
  hard-paths: ["ontology/**", "**/.gloss.yaml", "glossmark.yaml"]
  coverage-fail-under: 0                        # a percentage, or current (fail only below the base's)
  criticality-gates: { critical: HARD }         # minimum gate by criticality (docs/GOVERNANCE.md)
  waivers:
    - { finding: "gap:acme:library-platform:publishes:lib:HoldReady", owner: alice, expires: 2026-12-31, reason: "published by holds-worker" }  # expires is inclusive
```

- `owns.<prefix>`: a namespace this repo defines. `file` defaults to `ontology/<prefix>.gloss.yaml`. `tier` is `core` or `implementation`. `version` may repeat the ontology file's `version:`, which is the namespace version; `gloss check` fails when they disagree (GM115) and warns when only this one is set (GM114).
- `imports.<prefix>`: a namespace defined elsewhere. `source` is a local path (file or directory) today; `git+` and `https://` sources are parsed and rejected with a message until the fetcher lands (vendor the directory, or point at a sibling checkout). `version` is a range (`^1.2`, `~1.2.3`, `1.x`, `>=1.2 <2.0`) enforced against the resolved ontology's version; `gloss lock` pins the result in `glossmark.lock`. Only **published** concepts of an imported implementation namespace are referenceable (GM230). `tier` (`core` or `implementation`) applies when the imported file states none; a top-level `tier:` in the imported file wins, and `gloss publish` writes one. With neither, the namespace is read as core, and `gloss check` warns (GM113) when it has `published:` or `realizes:` concepts, because the published seam is then not enforced.
- `adoption:` (0 to 3) names the rung of the [adoption ladder](QUICKSTART.md#the-adoption-ladder) the repository has reached and caps what fails: at 0 `gloss check`, `gloss drift` and `gloss diff` report and exit 0; at 1 `gloss check` errors fail and drift and the gate report only; at 2 drift findings and HARD changes fail only when they touch a concept classified `high` or `critical`; at 3, the default when unset, everything `--fail-on` names fails. `gloss doctor` compares the level with what the tree has written ([ADR 0044](adr/0044-staged-adoption-levels.md)).
- `comment-styles:` extends the builtin comment table. A key is an extension with its dot (`.pkl`), an exact file name for files without one (`crontab`, `Jenkinsfile`), or a glob over the repository-relative path (`**/cron.d/*`; any key with `/`, `*`, `?` or `[`, and a glob without `/` matches at any depth). The most specific key wins: a file name, then the longest matching glob, then an extension, and every key wins over the builtin table. A value lists the tokens that open a comment: a line token (`#`) or a block pair separated by a space (`<%-- --%>`).
- `relations:` is the relation profile ([ADR 0042](adr/0042-relation-profiles.md)). `starter` is `implements`, `represents`, `verifies`, `documents`, `produces`, `consumes`, `part-of` and, in ontology files, `is-a`: `gloss check` hints (GM250, never an error, and `--strict` ignores it) at any other relation in a marker, a manifest or an ontology file, naming this key, and the AGENTS.md snippet and the MCP server list only the starter ones. `full` is every relation. Unset means `full`, so a repository written before the key existed reads as before; `gloss init` writes `starter`. The profile changes no graph: an advanced relation under `starter` still builds its edge. The seam's own keys (`realizes`, `replaced-by`, `published-as`) belong to every profile, since GM320 and GM340 ask for them, and so do the relations the tool writes from CODEOWNERS, Backstage or an import (`owns`, `same-as`, `derived-from`).
- `history:` holds the default of `gloss history --step`: `commit` (every commit, merges left out), `first-parent` (the main line, merges included) or `version` (one step per namespace version bump) ([ADR 0040](adr/0040-ontology-history.md)).
- `suggest:` holds the repository's defaults for `gloss suggest`; a flag of the same name overrides each one. `auto-accept-precision` (0 to 1) is the precision auto-accepted proposals must reach. The SOFT conf threshold is derived from it: the lowest conf whose proposals at or above it were at least that precise on the calibration data, which is the file `calibration` names when it exists, else the calibration shipped with the tool. When no conf reaches the target, nothing is auto-accepted, and `gloss doctor` says so. The threshold in force, its measured precision and the share of proposals it auto-accepts are printed by `gloss suggest`, `gloss suggest --eval` and `gloss doctor` ([ADR 0024](adr/0024-auto-accept-precision.md)). `labels` is a labels file (tab-separated path, symbol or `*`, relation, target) that `gloss suggest --calibrate` scores against instead of the repository's own links; `calibration` is where `gloss suggest --calibrate --write` writes the measured counts (tab-separated basis, proposals, correct, and the held proposals among them, whose target is deprecated and which are never auto-accepted, and how many of those were correct; a file with only the first three columns still reads). Paths are relative to the repository root.
- **Which threshold applies.** `suggest.auto-accept-precision`, when set, derives it. Otherwise `policy.soft-conf-threshold`, when set, is the threshold as written, which is the rule before ADR 0024 and what `gloss init` wrote until then. With neither, the default precision 0.9 derives it. When both are set, the precision wins and `gloss doctor` warns.
- Authoring uses CURIEs; the graph stores IRIs. Concept IDs are permanent: a rename is `deprecated: true` plus `replaced-by:`.
- Versions are semver: MAJOR removes or retypes a concept or changes is-a/part-of; MINOR adds or deprecates; PATCH touches labels and docs. `gloss diff` classifies the bump and gates a missing one HARD.

## `*.gloss.yaml` (one per namespace)

```yaml
namespace: circ
version: 0.3.0
concepts:
  CirculationService: { kind: system-type, realizes: lib:CirculationDesk }
  MarcParser:         { kind: process, part-of: CatalogIntake, internal: true }
  BookIntake:         { kind: process, realizes: lib:Cataloging, produces: [lib:Book] }
  DefaultLoanPeriod:
    kind: measure
    criticality: low                 # a wrong number confuses patrons; see docs/GOVERNANCE.md
    realizes: lib:LoanPeriod
    published: { as: lib:LoanPeriod }
    value: 21
    value-from: { path: services/circulation/loans/policy.py, symbol: LOAN_PERIOD_DAYS }
relations:
  produces: { lift: range-lcs }
```

Top-level keys: `namespace`, `version`, `tier` (optional; an owned file defaults to `owns.<prefix>.tier`, and an importer reads it before `imports.<prefix>.tier`), `doc`, `concepts`, `relations`.

`relations:` tunes a builtin relation or declares a new one (`relationDecl` in `schemas/ontology.schema.json`). A name that is not a builtin declares a relation; only the keys you set are applied, and `{}` is enough:

```yaml
concepts:
  Appeal: { kind: process, escalates-to: Review }
relations:
  escalates-to:
    doc: "A case that leaves this step goes to the target."
    domain: [concept]      # node types allowed as subject (default: concept)
    range: [concept]       # node types allowed as object (default: concept)
    inverse: escalated-from
    transitive: true
    surfaces: [impact, context]   # optional: the guards treatment, see below
```

A declared relation applies to every ontology file in the workspace, owned or imported. It is written only in ontology files, on a concept: an inline marker that uses one is an error (GM201), and so is an undeclared name (GM200, which shows this syntax). `gloss check` enforces `domain` and `range` (`concept`, `boundary`, `artifact`, `namespace`, `actor`) on every edge of the relation (GM220). `doc` is for readers of the file. `inverse` and `transitive` are metadata: they are recorded with the relation but the graph holds only the edges as written, so `escalates-to` adds no `escalated-from` edge and no closure is computed. Write the edge in the direction you will query. `surfaces` opts a concept-to-concept relation into the treatment `guards` and `constrains` get ([ADR 0015](adr/0015-guards.md)): `impact` makes `gloss impact` show it on both ends with an `<relation> code:` line listing the files linked to what it applies to, and `context` puts it on the `Applies here:` line of `gloss context --dir`. Without `surfaces` a declared relation is validated and written to the graph and nothing else reads it. An unknown surface is a warning (GM308).

`lift` only sets how `gloss drift` prints a boundary's derived set for the relation: `range-lcs`, already the builtin for `produces`, `consumes`, `publishes` and `subscribes`, shows it by its least common subsumer, and a violation adds a `rollup:` clause naming the members it summarizes; `none` shows the members on the consistent line, and a violation names only its concept and the declared set, with no `rollup:` clause. It never changes the comparison: a declared supertype covers a derived subtype for every compared relation ([ADR 0011](adr/0011-range-lcs-summary.md)).

`gloss publish` writes `<out>/<ns>/` with `ontology.jsonld`, a copy of this file and, for an implementation namespace, `graph.jsonl`. The copy states `tier:` and, for an implementation namespace, holds only the published concepts, like `ontology.jsonld`; an importer can point `source:` at the directory.

Concept keys:

| Key | Meaning |
| --- | --- |
| `kind` | `entity`, `process`, `capability`, `event`, `measure`, `constraint`, `resource`, `system-type` (required unless `is-a` is given). A concept without one inherits the kind of its nearest `is-a` ancestor that declares one; the graph node records it with `kind-from`, and every kind-dependent rule (`provisions`/`configures`/`deploys` on a resource or system-type lifting to `realizes`, domain and range) uses it. Parents that give different kinds are an error (GM306), and so is no kind anywhere up the chain (GM300). |
| `is-a`, `part-of`, `has-part` | Taxonomy and partonomy. Bare names are in the file's namespace. |
| `realizes` | Implementation → core. Every impl concept carries this or `internal: true` (GM320). |
| `published: { as: <core> }` | The single seam into the business view and across repos. `as:` must name an existing core concept (GM330). |
| `internal: true` | Engineering-private mechanism; realizes nothing, never crosses repos. Left out of concept coverage and the `untested` finding unless its effective criticality is `high` or `critical`. |
| `deprecated`, `replaced-by` | Renames and successors. `replaced-by` is a CURIE or a full IRI; its namespace need not be imported when its prefix is under `prefixes:` (the successor is often in a new repository): `gloss check` reports it (GM341) only when the namespace is owned or imported, and `gloss landscape` reports a dangling successor across repositories. It is stored as a `replaced-by` edge ([ADR 0020](adr/0020-replacements-across-repos.md)). |
| `value` | A concrete value (used by published measures and constraints). |
| `value-from` | `{ path: pfinance/fire.py, symbol: swr }` or `{ path, line: 42 }`: the code the value comes from (the first line that assigns, annotates or defaults the symbol). In a YAML, TOML or JSON file `symbol` is a dotted key path, `{ path: config/ratelimit.yaml, symbol: policies.claims-write.per_minute }`; a bare key or a tail (`claims-write.per_minute`) works when it ends exactly one path, and GM360 names the candidates when it ends several. A list of such locations binds a value duplicated in several places (the Go API and the TypeScript page); a change to any of them is drift, and so is one of several `publishes-value` markers on the same concept. The first build records the line as the baseline, in a `value:<curie>` entry of `.glossmark/ledger.jsonl`; a later change to it without a change to `value` is a **published value drifted** finding in `gloss drift` (fails by default) and HARD in `gloss diff`. The graph's `value-fp` follows the live line, so the ledger is the only baseline `gloss drift` has: deleting the ledger, or regenerating `.glossmark/` from scratch, accepts the code as it is. `gloss diff` still compares the base graph's `value-fp` with the head's, so it catches a change inside one pull request. Changing both together moves the baseline; `gloss accept --value ns:X` confirms the code as is when the line still holds the value (a number in `value` equal to one in the line, 4% matching 0.04, or the text itself); otherwise it refuses and prints both, and `--force` confirms anyway (the drift line then names `gloss accept --value --force`). The marker form is `@gloss publishes-value .X scope=line` above the line; it also counts as `implements .X`, so the boundary holding the line realizes X and can declare it ([ADR 0017](adr/0017-published-values-implement.md)). `gloss bind <path>:<symbol> --as ns:X [--publish-as core:Y]` writes `value`, `value-from`, `published` and the marker from the code in one step and records the baseline ([DEMO.md](DEMO.md), [ADR 0047](adr/0047-bind-writes-the-whole-binding.md)). The viewer shows the live line. |
| `proposed: true`, `proposed-by` | The entry is a proposal, the ontology's `@gloss?`. Links to it resolve; it is HARD-gated until `gloss accept --concept` drops the flag. `gloss propose` writes these entries. |
| `planned` | The concept is specified and nothing implements it yet: `planned: true`, or `planned: { by: 2026-11-30, ticket: https://... }` with either key optional; `by` is an inclusive `YYYY-MM-DD` deadline (GM307 when malformed) and `ticket` is provenance the tool never reads. Orthogonal to `proposed` (review) and allowed on core and implementation concepts. The concept is out of concept coverage and of the `orphan` finding; `gloss drift` lists it as a plan item (`planned`) until the first `implements` or `represents` link reaches it, directly, through a concept that realizes it or through a subtype (`verifies` alone keeps it open, listed as verified, not implemented), then reports `planned-closed` until `gloss accept --planned ns:X` drops the key; past `by` it is `plan-overdue`. The graph node carries `planned`, `plan-by` and `plan-ticket`; `gloss context`, the `AGENTS.md` snippet and `search_concepts` mark it `PLANNED`. Dropping the key is AUTO in `gloss diff` and needs no bump ([ADR 0025](adr/0025-deriving-the-ontology.md) 6.1, [ADR 0034](adr/0034-ontology-first-increments.md)). |
| `aliases` | Other names people and agents use; `search_concepts` matches them. |
| `criticality` | `low`, `medium`, `high` or `critical`: how much a mistake here matters. Implementation concepts inherit the highest level of what they realize when unset. See [GOVERNANCE.md](GOVERNANCE.md). |
| any other key | A relation: `produces`, `consumes`, `publishes`, `subscribes`, `constrains`, `guards` (alias `applies-to`, [ADR 0015](adr/0015-guards.md)), `reverses`, `attaches-to`, or one declared under `relations:`. |

Write `doc` quoted (`doc: "One account (checking, savings)."`) or in block style. Inside a `{ }` flow mapping an unquoted doc ends at its first comma: the rest of the sentence becomes null-valued keys that add no edge, and nothing downstream notices. `gloss check` reports the cut doc (GM305) and any other null key (GM304); `gloss propose` writes quoted docs.

Tier rules: a core file may not reference any implementation namespace (GM310); core concepts realize nothing (GM312). The own-subject rule: a repo may only add edges whose subject is in a namespace it owns, so `hw:CurbsidePickup is-a lib:HoldFulfillment` is allowed and `lib:HoldFulfillment has-part hw:CurbsidePickup` is rejected (GM400). The hierarchies are acyclic: an `is-a` cycle, a self-loop included, is an error (GM370), because every concept on it would subsume every other and widen every declaration that names one; so is a `part-of`/`has-part` cycle in either tier (GM371). Each error names the members in order with the file and line of every edge. GM320 follows `is-a` and `part-of` (or `has-part` written on the whole) to a concept that realizes something (or is core, internal, or presents or hosts something); two concepts that are only part of each other do not satisfy it.

## `.gloss.yaml` (boundary manifest, any directory)

```yaml
boundary: acme:circulation-svc
level: container                 # domain | system | container | component
label: Circulation service
part-of: acme:library-platform  # optional: default the boundary of the nearest manifest in an enclosing directory; [] for none
realizes: [circ:CirculationService, lib:Cataloging, lib:Return]   # or [inherit, circ:Extra]: what the nested boundaries declare, plus additions
produces: [lib:Media]            # holds and the four flows take inherit too
holds: [lib:Loan]                # concepts whose data this boundary owns; code under it must represent them
configures: [lib:LoanPeriod]     # concepts whose value this boundary edits at runtime (an admin page)
guarded-by: [circ:StaffAuth]     # mechanisms every artifact under this directory sits behind (ADR 0015)
default-namespace: circ          # .Name in markers below resolves to circ:Name
allowed: [lib:Media, lib:Book, circ:Catalog*, circ:Return*]   # optional narrowing; see below
generated: ["gen/**"]
owner: circulation-eng
criticality: high                # optional; else the highest of what the code realizes, represents or configures, else the parent's (not for a boundary that only presents or hosts)
criticality-floor: true          # optional: the level above is a floor for every artifact beneath this directory
deprecated: true                 # optional: the boundary is being retired
replaced-by: acme:loans-svc      # optional: the boundary taking over, here or in another repository
retire-by: 2027-03-31            # optional: when it is due to go (YYYY-MM-DD)
planned:                         # optional: capability the boundary will have (ADR 0034)
  realizes: [lib:Renewal]        #   realizes, produces, consumes, publishes, subscribes
  publishes: [lib:LoanRenewed]
  by: 2026-11-30                 #   inclusive deadline for the block
```

An unknown key is an error (GM110) reported at its own line, but the rest of the manifest still applies: the boundary exists and its files stay in it, so one misspelt key does not move them to the parent boundary. `planned:` declares what the boundary will realize, produce, consume, publish or subscribe to by a date: an ordinary declaration for the rollup, for `inherit` in an enclosing manifest and for the derived `allowed` set, so the agent implementing it is inside the boundary's contract from the first marker. Only the drift finding differs: `gloss drift` reports a planned entry nothing under the boundary derives as a plan item (`planned`, never failing by default) instead of a gap, reports it `planned-closed` once code derives it under the same subsumption rule that closes a gap (move it to the plain list), and `plan-overdue` once `by` has passed ([ADR 0034](adr/0034-ontology-first-increments.md)). `deprecated`, `replaced-by` and `retire-by` mark a boundary that is being split out or retired; they are carried on the boundary node, and a link into a deprecated boundary is warned (GM222) and HARD in the gate, as for a deprecated concept ([ADR 0007](adr/0007-retiring-boundaries.md)). `deprecated` with `replaced-by` naming another boundary declares a migration: drift reports two unrelated boundaries realizing or holding the same concept as an `overlap` unless such a migration links them, and a deprecated boundary that still has code after its `retire-by` day is `overdue`, which fails `drift` ([ADR 0019](adr/0019-migration-overlap.md)).

The nearest ancestor manifest applies to every file beneath it, as with CODEOWNERS; manifests are optional at every level. Nesting is containment: a manifest that names no `part-of` is part of the boundary of the nearest manifest in an enclosing directory, so the parent's rollup counts the child's code and `inherit` reaches it ([ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)). `part-of` may name any boundary instead, not only the one in the parent directory, so a logical parent (a domain, a platform) can live beside its children; that boundary keeps the level, directory and file of its own manifest, and its directory may hold nothing but the manifest. A component may contain components: views nest them by `part-of` and fold both at any zoom above `component` ([ADR 0035](adr/0035-components-under-a-flat-package-tree.md)). `part-of: []` makes a nested boundary part of nothing. A `part-of` cycle among boundaries is an error (GM510): each would roll up the other's code. A boundary named only by `part-of`, with no manifest, is a stub with no level; views place it one level above its children. `realizes`, `holds`, `presents`, `hosts`, `configures`, `produces`, `consumes`, `publishes` and `subscribes` are the declared intents that `gloss drift` compares with what the code derives: `implements` (and `provisions`, `configures`, `deploys` on a resource or system-type) derive `realizes`; `represents` satisfies a declared `holds` on any kind of concept (a table that stores a measure's values satisfies `holds:` for it, [ADR 0013](adr/0013-data-shapes-and-coverage.md)) but never derives one, since a copy or a wire schema represents data it does not own ([ADR 0037](adr/0037-holds-is-declared-ownership.md)); `configures` lifts as itself on any kind, as well as to `realizes` on a resource or system-type; the rest lift as themselves. The flows a concept declares (`ClaimFiling: { publishes: [ClaimFiled] }`) reach the boundaries whose code implements it as intent: drift compares them with the manifest, where a declared subtype or part refines them, but only the code's own markers close a gap ([ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)). A manifest `publishes` or `subscribes` of a concept that is not an event (often after an upstream retype) is warned by `gloss check` (GM225), and a drift gap over code that links to the declared concept only by relations that do not lift names those links. A relation the manifest does not declare is not compared. An explicit empty list is a declaration of none: `realizes: []` on a boundary that is only a surface makes any code under it that implements something a violation (`hpb:storefront realizes hp:Pricing, declared realizes []`), and a `presents` or `hosts` gap over code that implements the concept says so ([ADR 0012](adr/0012-surfaces.md)). A container that only contains its components writes `realizes: inherit` (optionally with additions, `realizes: [inherit, circ:Gateway]`): its declared set is the union of what the boundaries nested inside it declare, so the list is not repeated at every level; gaps in inherited entries are reported by the child that declared them. `holds`, `produces`, `consumes`, `publishes` and `subscribes` take `inherit` the same way (`holds: [inherit, lib:LoanStatus]` at a root that keeps code tables beside its components); `presents`, `hosts` and `configures` describe the boundary's own surface and do not. A nested boundary that realizes (or holds, produces...) concepts but declares no such relation of its own while an ancestor inherits it is reported once, on that boundary's manifest (`o:web realizes 5 concepts but declares no realizes; o:clinic inherits from it`), not as one violation per concept at the parent. When a boundary has several violations of one relation, the first lists the declared and derived sets and the others name only their concept. A concept inherits `realizes` through `is-a` and a part realizes its whole, so `CsvImporter: { is-a: Importer }` needs no `realizes:` line of its own and code that implements a part of a pipeline satisfies a manifest that declares the pipeline. The reverse does not hold: a manifest that declares a part is not satisfied by code that implements the whole ([ADR 0009](adr/0009-hierarchy-direction.md)).

`guarded-by` names the mechanisms every artifact under the directory sits behind, so a boundary whose handlers all pass one authentication need not list each handler under `guards:` in the ontology. Code under it is guarded code as if the ontology said so: `gloss impact` shows `guarded by circ:StaffAuth (high)` on every file there and lists the files under the guard's `guarded code:`, `gloss context --dir` names it on the `Applies here:` line, and `gloss diff` reviews a change there at the guard's level without the code inheriting it. It is not a declared intent: drift does not compare it, and it adds nothing to `allowed`. Drift reports `unguarded` for a handler under the directory (an artifact with a symbol anchor and a link that is not a test or a document) that carries none of the guard's decorators when another handler there does; the decorators are named by the declarations that `implement` the guard. A guard applied by middleware decorates no handler, and its declaration is taken at its word.

`allowed` is a deliberate narrowing, not a requirement. When it is absent the allowed set is derived: the `default-namespace`, every concept the manifest declares (`realizes`, `produces`, `consumes`, `publishes`, `subscribes`, `holds`, `presents`, `hosts`, `configures`), every concept a declared one covers in `gloss drift` (its `is-a` and `part-of` descendants, followed along mixed chains, and the implementation concepts that realize it or one of those descendants, so a boundary declaring `cyc:CatalogueIngestion` admits `spk:ShimanoXmlImporter`, which is-a `spk:Importer`, which realizes it), the core concepts a declared implementation concept realizes (not the wholes it is part of), and whatever the boundaries nested inside it allow (a container holds its components). A link outside the derived set is a warning in `gloss check` (GM503) and HARD in the PR gate; outside a written list it is an error (GM502) and HARD. `gloss check --explain` prints the effective set per manifest, grouped by source: a header with the number of entries, then one line each for the default namespace, the declared concepts (each with the number of concepts it covers, `cyc:Product (+17 below)`), the cores realized by a declared implementation concept, the `listed` extras and the nested boundaries (each with the entries it adds). `--format json` prints one record per manifest with every entry and its reason (`default-namespace`, `declared`, `covered`, `realized`, `listed`, `nested`, or `allowed` for a written list) and the concept or boundary it comes `from`. A manifest that declares nothing and names no default namespace restricts nothing. Write `allowed:` only to permit less than the derived set (a list of its own), or to add a concept the boundary uses without declaring it: `allowed: [derived, gm:Confidence]` is the derived set plus `gm:Confidence`, the way `realizes: [inherit, ...]` extends what children declare. `criticality` classifies the boundary for review (see [GOVERNANCE.md](GOVERNANCE.md)); `gloss check` warns when it is declared below a concept the code realizes.

## `views.yaml`

```yaml
views:
  business:
    include: [lib:*]
    collapse: { "circ:*": via realizes }     # circ nodes fold into what they realize; the realizes edges they fold along are not drawn
    show-published: true
    relations: [produces, consumes, constrains]
    lift: range-lcs                           # {Book, DVD} shows as Media
    zoom: system
  engineering:
    include: [lib:*, circ:*]
    expand: { part-of: 2 }                    # two levels of parts
    zoom: container
  loan-policy:                                # curated: it names its concepts
    include: [lib:LoanPeriod, lib:Loan, circ:DefaultLoanPeriod]
    zoom: code
  checkout:                                   # a saved slice
    slice: [lib:Checkout]
    zoom: code
```

Two presets ship (business, engineering) and are generated when the file is absent. An unknown key, at the top or in a view, is an error (GM118) at its own line; the rest of the file still applies. Zoom (`landscape`, `system`, `container`, `component`, `code`) decides which boundary levels appear; artifacts appear only at `code`.

A view whose `include:` names at least one concept (not only `ns:*` globs) is **curated**: the viewer opens it with every box open, and it keeps only the artifacts that link to a named concept and the edges with at least one named end.

A view with `slice:` (CURIEs or globs of concepts and boundaries) is a **saved slice**: instead of an `include:` list it shows the feature slice of those seeds, with context, computed by the same rules as `gloss slice` ([ADR 0023](adr/0023-feature-slices.md)) on every build, so it tracks the code instead of a hand-kept list. Its concepts, boundaries and artifacts are the slice's nodes; it is curated, and the viewer opens it with the slice active. `slice:` and `include:` together are an error. The projection repeats the seeds as `slice`, `gloss impact` and MCP `impact_of` name the saved slices a change touches, and `gloss diff` reports a change to the slice as a change to that view.

In a projection every concept also carries the boundary it sits in (`boundary`). Candidates are the boundaries whose code realizes it and those whose manifest declares `holds` for it, or for an implementation concept that realizes it; code that only represents a concept places nothing ([ADR 0037](adr/0037-holds-is-declared-ownership.md)). A boundary whose own code links to the concept, and whose manifest declares it (`realizes` or `holds` it, or an implementation concept that realizes it), is strongest; then one whose own code links to it without the declaration; then one whose manifest only declares it; then one that reaches it by lifting through other concepts. "Own code" is a marker that names the concept, or names an implementation concept that realizes it in one hop, so `implements hp:OrderPlacement` and `implements .OrderIntake` (which realizes it) count the same, and the CURIE style of a marker never decides the box ([ADR 0012](adr/0012-surfaces.md)). A service that declares `holds: [hp:Order]` keeps the entity when a gateway schema also represents it ([ADR 0013](adr/0013-data-shapes-and-coverage.md)). Among the strongest candidates the deepest wins, or the nearest boundary enclosing all of them when several unrelated ones remain. A `part-of` whole is never placed deeper than one of its parts: when its box lies inside a part's box it moves to the nearest boundary enclosing its own and all its parts' boxes ([ADR 0010](adr/0010-deep-hierarchies.md)), so `cyc:OrderFulfilment` sits in the fulfilment container whose `engine.py` implements `spk:FulfilmentEngine`, not in the leaf component that declares it. Pages that `presents` a concept never place it. The viewer draws a boundary as a box around those concepts, closed at first; the reader opens boxes to drill in. A box with no other box beside it (the one system at system zoom) opens at first and draws no interface edges, since it has no neighbours for them to face ([ADR 0039](adr/0039-a-core-view-that-reads.md)). Projections also carry each node's effective `criticality` (the highest of its own and of everything folded into it), and `deprecated`, `replacedBy` (and `retireBy` on boundaries) for what is being retired; the viewer draws deprecated nodes dotted and names the successor in the concept pane. A planned concept carries `planned`, `planBy` and `planTicket`, and an edge that only a manifest's `planned:` block declares carries `planned`; the viewer draws both faint, rings a plan in dashed red once its `by` date has passed, and offers a **Plan** filter. View diffs ignore the flag, so dropping it stays bookkeeping ([ADR 0038](adr/0038-planned-in-views.md)). A migration view reads old next to new with `relations: [realizes, holds, replaced-by]`.

A concept no boundary realizes or holds is placed by its flows when one of them produces or publishes it: it sits in the nearest boundary enclosing every shown boundary that produces, consumes, publishes or subscribes to it, and its reason names them (`inside acme:library-platform; published by acme:library-platform`). A single producer places it in its own box; consumers alone never place it, since what they consume comes from outside ([ADR 0036](adr/0036-flow-concepts-sit-in-the-box-that-encloses-them.md)). A concept neither places stays **unplaced**: the viewer draws it outside every box, in a dashed group named for its `placement`. Every concept in a projection carries one, with the reason in `placementReason` (such as `produced by acme:circulation-svc`); the first value that applies wins:

- `housed`: inside a boundary box (`boundary` is set).
- `shared`: unrelated boundaries realize or hold it (itself or its parts) and no boundary encloses them all; give them a common parent manifest, or let the concept stay shared.
- `flow`: a boundary produces, consumes, publishes or subscribes to it, but nothing shown produces or publishes it (an input from outside), or what does shares no enclosing boundary with what uses it: the seam between unrelated systems, such as several top-level boundaries in one repository, or repositories in a `gloss landscape` that are not part of one system.
- `bound`: its value is bound to code with `value-from` or `publishes-value`.
- `surface`: only pages `presents` it, shells `hosts` it or value editors `configures` it.
- `shape`: code represents it, but no boundary declares `holds` for it: a copy, a cache or a payload of data owned elsewhere, or an owner that has not declared it.
- `planned`: the concept is planned and nothing else places it; add it to the `planned:` block of the manifest that will build it ([ADR 0038](adr/0038-planned-in-views.md)).
- `unlinked`: none of the above. Usually nothing links to it at all, which `gloss drift` reports as an orphan; otherwise the reason names the links it has, such as `documents` from code.

Boundaries and artifacts carry no `placement`. The viewer draws a part under its whole when the whole is shown, so only concepts without a shown whole go in a group.

## Evidence (`gloss harvest`, experimental)

`gloss harvest` prints evidence of a repository's vocabulary as JSON lines on stdout, for a derivation to reason over ([ADR 0025](adr/0025-deriving-the-ontology.md)); nothing is written to the repository. The first line is `{"type":"evidence","format":1,"generator":...}`; every other line is one observation:

```json
{"id":"ev:3f2a91c04b17","unit":"services/circulation","signal":"table","surface":"loans","source":{"family":"data","path":"services/circulation/loans/models.py","line":17},"context":["class:LoanRow"]}
```

`signal` is one of a closed list and fixes the `family` (`code`, `data`, `behaviour`, `surface`, `doc`, `history`, `vocabulary`, `reference`, `tracker`, `doc-connector`); `context` carries typed hints (`is-a:`, `part-of:`, `iri:`, `kind:`, `table:`, `fk:`, `enum:`, `of:`, `in:`, `attr:`, `member:`, `alias:`, `renamed-to:`). From git history a record carries `first_seen` (the first commit that added the surface) and `last_seen` (HEAD for the current tree, the last commit naming it for a rename), as `YYYY-MM-DD`; `--no-git` drops them. `--reference <file>` (repeatable; `.ttl`, `.nt`, `.rdf`, `.owl` or `.jsonld`) reads an owner-supplied vocabulary into `reference-term` evidence with the IRI as `locator`: in `--cluster` a term only it names is no candidate, its label breaks a naming tie between the repository's own surfaces, and its `subClassOf` and part-of relate two candidates that both have their own evidence (`is-a:`/`has-subtype:`, `part-of:`/`has-part:` in `related`). A record never holds source text: a repository location, or a `uri`, `locator` and `hash` for a source outside it. `gloss harvest --ingest <file>` validates records a connector or tracker reader produced against the same rules (`schemas/evidence.schema.json`) and merges them; `--about <term>` keeps only the observations that name or mention a term (with `--format text`, one line each), the way to read the rule sentences and state changes behind a concept; `--cluster` prints candidate concepts instead: `{key, name, named_by, category, families, signals, naming, named_as, mentions, units, surfaces, related, evidence, first_seen, last_seen}`.

## Tool-maintained files under `.glossmark/`

- `graph.jsonl` — the canonical graph, one JSON record per line, deterministically sorted so `git diff` is meaningful (see `docs/GRAPH.md`). Its first line carries `"format"`; a newer format is refused, not misread.
- `glossmark.lock` (repo root, committed) — resolved version, range, source and content hash per import, written by `gloss lock`.
- `imports/<prefix>@<version>.gloss.yaml` (committed) — the copy of each locked import that `gloss lock` vendors; commands resolve the import from it while its hash matches the lock ([ADR 0002](adr/0002-lock-pins-imports.md)).
- `import-record.jsonl` (committed) — what `gloss import` last read from its source for each concept it wrote: `{ns, name, doc, aliases}` after a `{"type":"header","format":1}` line. A re-run updates a doc or an alias list only when the source changed since, and does not re-add a concept deleted or renamed after an import ([ADR 0016](adr/0016-adoption-scaffold-and-imports.md)). Delete a line to let the importer treat that concept as new again.
- `plan.jsonl` (committed) — the plan record of ontology-first increments ([ADR 0034](adr/0034-ontology-first-increments.md) section 4), written by the `curate-increment` skill and read by `gloss` with the workspace. A `{"type":"plan","format":1,"generator":…}` header, then one record per line: a `brief` per increment `{increment, date, actor, owner, answers}` (the ticket URI, the day, and the owner's interview answers by step), a `decision` per entry written or changed `{increment, subject, decision, reason, actor}` (`decision` one of `added`, `widened`, `changed`, `published`, `criticality`, `declined`, `removed`), and a `deviation` per departure found while implementing `{increment, subject, disposition, reason, actor}` (`disposition` one of `absorbed`, `reopened`, `reverted`). `date` is `YYYY-MM-DD`. A line that is not a valid record, has an unknown field or misses a required one is an error (GM124) at its own line; the other lines still load. The session-start briefing (`gloss context`) lists the open and closed plan items of the agent's directory, and MCP `impact_of` returns a `plan` block with the items the changed files close and those still open.
- `context.jsonld` — the JSON-LD context that makes `graph.jsonl` RDF-loadable.
- `viewer.html`, `views.js`, `views.json` (not committed) — `gloss view` writes the page, the data script it loads (a plain `<script src>`, so opening the file from disk works) and the same data as JSON for tools; `--inline` embeds the data in one page instead. The data includes `slices`, the precomputed feature slice of every concept and boundary as interned index lists (`ids`, `roles`, `steps`, and `of`: seed → `[node, role, via step...]`), capped in size ([ADR 0023](adr/0023-feature-slices.md)). With `--diff` it holds `diff`, that impact; with `--history` it holds `history`, the `gloss history --all --format json` record ([ADR 0040](adr/0040-ontology-history.md)).
- `ledger.jsonl` (committed) — provenance and review state per marker: `{marker_id, path, relation, targets, actor, model, conf, created, status, reviewed_by, reviewed_at, anchor_fingerprint, rationale, review_reason, previous_ids}`. `rationale` is the author's `note=`; `review_reason` is the reviewer's `gloss reject --reason`. `status` is `removed` only for a marker that disappeared without a decision; `previous_ids` lists the ids a marker had before a review command rewrote its target (`propose --from-new`, `reject --concept --remove`), whose row moved to the new id ([ADR 0027](adr/0027-review-trail-across-rewrites.md)). It is the only store of accepted, rejected and stale decisions, and of each published value's baseline (`value:<curie>` entries, see `value-from`), so it belongs in git like the graph. `gloss init` (and the first `gloss build`) writes it with only its header line, `{"type":"ledger","format":1,...}`, before any marker exists. `actor` is fixed at the marker's first appearance (see `docs/QUICKSTART.md`). Exportable as PROV-O JSON-LD with `gloss export --prov`: a `prov:Activity` per row (`prov:wasAssociatedWith` its author, `gm:status`, `gm:relation`, `gm:target`, `gm:path`, `gm:rationale`, `gm:reviewedBy`, `gm:reviewedAt`, `gm:reviewReason`, `gm:previousId`) and a `prov:Agent` per author and reviewer, also typed `prov:Person` for `human:` and `prov:SoftwareAgent` for `agent:`.
