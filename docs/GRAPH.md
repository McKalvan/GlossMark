# The canonical graph

Everything downstream reads `.glossmark/graph.jsonl`, never the source. Adding a consumer never touches the extractor.

## Records

Line 1 is the context: `{"type":"context","format":1,"generator":"gloss 0.2.0","prefixes":{...},"@context":"./context.jsonld"}`. `format` is the record format version; a reader refuses a newer one (see `docs/VERSIONING.md`).

Node records (`"type":"node"`), sorted by node type then IRI:

```json
{"type":"node","node":"concept","id":"https://onto.acme.dev/library/Book","curie":"lib:Book","ns":"lib","tier":"core","kind":"entity","aliases":["volume","paperback","hardcover"],"file":"ontology/lib.gloss.yaml","line":9}
{"type":"node","node":"boundary","id":"https://arch.acme.dev/boundaries/circulation-svc","curie":"acme:circulation-svc","kind":"container","criticality":"high","criticality-from":"lib:Checkout","owner":"circulation-eng","dir":"services/circulation",...}
{"type":"node","node":"artifact","id":"urn:gloss:artifact:services/circulation/cataloging/intake.py#catalog_book","kind":"function","path":"services/circulation/cataloging/intake.py","anchor":{"scope":"symbol","symbol":"catalog_book","start":7,"end":8,"fingerprint":"sha256:..."},"boundary":"https://arch.acme.dev/boundaries/circulation-svc"}
```

Edge records (`"type":"edge"`), sorted by subject, predicate, object, source, path, line:

```json
{"type":"edge","s":"urn:gloss:artifact:...#catalog_book","p":"implements","o":"https://onto.acme.dev/circulation/BookIntake","source":"inline","prov":{"path":"services/circulation/cataloging/intake.py","line":5,"col":3,"scope":"symbol","symbol":"catalog_book","fingerprint":"sha256:...","id":"m-5691...","actor":"human:alice","raw":".BookIntake"}}
{"type":"edge","s":"https://arch.acme.dev/boundaries/circulation-svc","p":"realizes","o":"https://onto.acme.dev/library/Cataloging","source":"derived","prov":{"path":"services/circulation/cataloging/intake.py","line":5,"rule":"realization-lift","via":["services/circulation/cataloging/intake.py#catalog_book","circ:BookIntake"],"steps":["realizes lib:Cataloging"]}}
```

`source` is `declared` (ontology files, manifests), `inline` (markers), `manifest` (a `links:` entry in a manifest or `glossmark.yaml` that maps a path or symbol to the concept, [ADR 0041](adr/0041-manifest-links.md); `prov.path` and `prov.line` name the code and `prov.from` the entry, `path:line`), `inferred` (inferrers such as test paths) or `derived` (rollup rules). Proposals carry `"proposed":true`; confidences `"conf":0.72`. A concept node written with `planned:` carries `"planned":true` and, when given, `"plan-by"` and `"plan-ticket"`; a manifest's `planned:` entries are declared edges whose provenance carries `"rule":"planned"` ([ADR 0034](adr/0034-ontology-first-increments.md)). A namespace node carries `"decls-fp"`, a fingerprint of what its ontology file says outside the concepts (iri, tier, doc, the `relations:` block), which `gloss diff` compares so an edit there is reported (`namespace-changed`, HARD) even when a bookkeeping change in the same file explains it to the hard-path rule. A marker written with the alias `tests` is stored as `verifies` with `"alias":"tests"` in its provenance, so every test link is a `verifies` edge.

Every `file`, `path` and `prov.path` is relative to the repository root, so the graph does not depend on where it is checked out. An imported ontology outside the root keeps its `../` form (`"file":"../circulation/ontology/lib.gloss.yaml"`).

Special object IRIs: `urn:gloss:new:circ:NEW:DamageCheck` (a proposed new concept), `urn:gloss:glob:circ:*` (a `may-modify` glob), `urn:gloss:unresolved:x:Y` (unknown prefix).

## Derivation rules

1. **Containment.** An artifact under a manifest is `part-of` that boundary; boundaries chain upward via `part-of`. A manifest that names no `part-of` is part of the boundary of the nearest manifest in an enclosing directory (a declared edge with `"rule":"nearest-manifest"`), so nesting is containment unless `part-of` says otherwise; `part-of: []` makes a boundary part of nothing ([ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)).
2. **Realization lift.** If artifacts in boundary B `implements` X then B `realizes` X, and everything X stands for: the core concepts it realizes or is published as (transitively), the wholes it is `part-of` and what they realize, and what its `is-a` ancestors realize. `provisions`, `configures` and `deploys` on a `resource` or `system-type` concept lift to `realizes` the same way, so infrastructure, configuration and deployment boundaries can declare what they stand up. Kinds are effective kinds: a concept with none inherits its nearest `is-a` ancestor's, recorded as `kind-from` on the node ([ADR 0009](adr/0009-hierarchy-direction.md)). `represents` lifts to the boundary as itself, whatever the kind, and never to `holds`: a copy or a wire schema represents data it does not own, so ownership is declared (`holds: [pf:Transaction, wh:CountVariance]`) and drift checks that code under the boundary represents each held concept, or one that realizes it ([ADR 0013](adr/0013-data-shapes-and-coverage.md), [ADR 0037](adr/0037-holds-is-declared-ownership.md)). `presents` (a page) and `hosts` (a shell) lift as themselves, directly from markers and through the concept an artifact implements, and never to `realizes` ([ADR 0001](adr/0001-presents-and-hosts.md)). `configures` lifts as itself on a concept of any kind, so a page that edits a limit's value can be declared and compared ([ADR 0012](adr/0012-surfaces.md)). Intended relations declared on X and on the concepts it realizes (`produces`, `consumes`, `publishes`, `subscribes`) lift to B as well, as intent: their edges carry `"rule":"intended-lift"`, and drift compares them with the manifest apart from what the code itself produces, consumes, publishes or subscribes to (see Comparison, [ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)); `represents` and `verifies` (with its alias `tests`) lift as themselves; the `test-paths` inferrer turns `implements` and `represents` under a test path into `verifies`. Every lifted edge records its whole derivation ([ADR 0010](adr/0010-deep-hierarchies.md)): `via` lists the artifact, the concept it links and every concept passed through, and `steps` spells out the hops, so `spw:feeds realizes cyc:CatalogueIngestion` from code implementing `spk:ShimanoXmlImporter` has `steps` `is-a spk:XmlFeedImporter`, `is-a spk:FeedImporter`, `is-a spk:SupplierImporter`, `is-a spk:Importer`, `realizes cyc:CatalogueIngestion`. The two hierarchies lift differently on purpose: the wholes above a part become derived facts of the boundary (implementing a step implements part of the whole), while `is-a` ancestors do not (implementing `ShimanoXmlImporter` is not implementing every `Importer`); an ancestor only passes on what it realizes, and shows in `via` and `steps`.
3. **Taxonomic lift** (`lift: range-lcs`). A set `{Book, DVD}` is summarized as its least common subsumer `Media` in views and in the drift report ([ADR 0011](adr/0011-range-lcs-summary.md)). The lift is partial: each maximal subset of members that share a subsumer is lifted on its own, so `{Claim, MotorClaim, FloodClaim, Assessment, Payout}` reads `{Assessment, Claim, Payout}` and a violation names what each lifted concept summarizes (`(cl:Claim from cl:Claim, cl:FloodClaim, cl:MotorClaim)`) ([ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)). It is a summary only. The comparison always subsumes: every compared relation is an existential claim ("this boundary produces some `Media`"), so a declared supertype covers a derived subtype whatever `lift` says. In drift the summary follows the relation's `lift`, `range-lcs` by default for `produces`, `consumes`, `publishes` and `subscribes`, `none` to print members; a violation names the members it summarizes (`rollup: produces {cyc:PoweredDevice} (from cyc:ElectronicRearDerailleur, cyc:FrontLight)`). In a view it follows the view's `lift:`. Each lift needs a unique subsumer: when the members of a subset share several incomparable minimal subsumers (`ElectronicRearDerailleur` and `ElectronicFrontDerailleur` are both a `Derailleur` and a `PoweredDevice`), or a member could join either of two subsets, those members are not lifted, drift appends `(no unique subsumer: cyc:Derailleur, cyc:PoweredDevice)` to the set, and the projection's edges carry `noUniqueSubsumer`. A curated view never lifts the concepts its `include:` names, since those edges are what it was written to show.
4. **Implied relationships.** A `publishes`/`subscribes` or `produces`/`consumes` pair on one concept between two boundaries implies `depends-on` (consumer → producer) unless declared. Across repositories this is the context-map edge `gloss landscape` draws, in the same direction; it leaves out an edge between a boundary and one that contains it (through `part-of` or a manifest in an enclosing directory).
5. **Generalization.** Views fold implementation into core via `collapse: via realizes`: a concept folds into what it realizes or is published as, else where the whole it is part of folds, else where its `is-a` parent folds, so every concept whose realization closure reaches a core concept is listed in that node's `folded`. A feature slice (`gloss slice`, a `slice:` view) is the other projection: from a seed it follows each relation in one fixed direction ([ADR 0023](adr/0023-feature-slices.md)). Each concept in a projection (`views.json`) carries the `boundary` it sits in, its `placement` (`housed`, `shared`, `flow`, `bound`, `surface` or `unlinked`) and a `placementReason`; see [FILE-FORMATS.md](FILE-FORMATS.md#viewsyaml).
6. **Criticality.** Every concept, boundary and artifact carries an effective `criticality` and its provenance (`criticality-from`, the node it was inherited from, and `criticality-source`, the node at the end of that chain that declares it): declared levels win; implementation concepts inherit from what they realize, boundaries from what their code realizes (else their parent), artifacts from their boundary and the concepts they link to. See `docs/GOVERNANCE.md`.

## Comparison

For each boundary and each of `realizes`, `holds`, `presents`, `hosts`, `configures`, `produces`, `consumes`, `publishes`, `subscribes` that the manifest declares (an explicit empty list such as `realizes: []` included: it declares none, so everything derived is a violation):

| Declared | Derived from code | Result |
| --- | --- | --- |
| `circulation-svc produces Media` | boundary produces {Book, DVD} ⊑ Media | Consistent |
| `circulation-svc produces Media` | an agent adds `@gloss produces lib:Laptop` | **Violation**: boundary exceeds its declared capability |
| `circulation-svc produces Media` | nothing produces DVD | **Gap**: intended capability not implemented, or the core is wrong |
| `circ:X realizes lib:Y` | X has no artifacts | **Orphan** impl concept |
| `lib:Renewal: { planned: { by: 2026-11-30 } }` | nothing implements or represents it (a `verifies` link alone does not count) | **Planned**: a plan item, not an orphan; **plan-overdue** after `by`; **planned-closed** (drop `planned`) once code reaches it |
| `planned: { realizes: [lib:Renewal] }` in a manifest | nothing under the boundary implements it | **Planned**: a plan item, not a gap; closes under the gap's subsumption rule |
| none | artifact links `circ:NEW:DamageCheck` | **Rogue** concept; becomes a decision request |

A declared concept covers a derived one when they are equal, when the declared one subsumes it (`is-a*`), or when the derived one realizes it (impl → core, and a part realizes its whole). Both hierarchies point one way ([ADR 0009](adr/0009-hierarchy-direction.md)): a declared whole covers a derived part, as a declared supertype covers a derived subtype, but a declared part never covers a derived whole, so code implementing `OrderFulfilment` under a manifest that declares only its step `ScanConfirm` is a violation, and `ScanConfirm` stays a gap until code implements it or one of its parts. The wholes lifted from a declared part's own code are consistent. Internal concepts and event emitters are exempt from the `realizes` comparison.

A concept's own flows are intent, not code ([ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)). For `produces`, `consumes`, `publishes` and `subscribes` drift keeps two sets: what the code derives (markers such as `@gloss publishes cl:MotorClaimFiled`, and what they lift to) and what the concepts the code implements intend (`ClaimFiling: { publishes: [ClaimFiled] }`), the JSON `intended` field. Only the code's set closes a gap: a manifest that declares `subscribes: [cl:PayoutFailed]` over code that implements `cl:PayoutNotification`, whose concept subscribes to it, has the gap `declares subscribes cl:PayoutFailed and cl:PayoutNotification intends it, but no code under it subscribes to it`. The intended set is compared with the manifest on its own: an intended concept is consistent when a declared concept covers it or when the manifest declares a refinement of it (a subtype, a part, a concept that realizes it), so a container that implements `ClaimFiling` may declare only the `MotorClaimFiled` it publishes; otherwise it is a violation (`publishes cl:ClaimFiled by intent (cl:ClaimFiling intends it), but declares publishes {...}`).

Violations are reported by cause ([ADR 0010](adr/0010-deep-hierarchies.md)). A concept that is only derived because another uncovered concept lifted it (the wholes above a part, the cores a subtype realizes) is listed under that concept's finding (`lifted`), so one marker on a part five levels down is one violation, not five. Under `realizes: inherit` (and `inherit` on `holds`, `produces`, `consumes`, `publishes` and `subscribes`, [ADR 0026](adr/0026-rollup-intent-nesting-inherit.md)), a concept derived from code in a nested boundary is judged where the inheritance ends: walking down from the boundary toward the code, the first boundary that does not inherit. If it declares the relation, its own comparison reports the concept and its ancestors stay quiet; if it declares nothing, the omission is one violation at that boundary, naming its manifest and the ancestors that inherit from it. The first violation of a boundary and relation names the declared set and the others refer to it; the full derived set is in `--all` and in the JSON `derived` field.

## Querying

`gloss export --sqlite graph.db` writes tables `nodes`, `edges`, `prefixes` and views `is_a_closure`, `part_of_closure`, `realizes_closure`, `concept_artifacts` (recursive CTEs). Besides the graph's nodes, `nodes` holds a `node='file'` row (id `urn:gloss:file:<path>`) for every in-scope file with no marker beneath a `criticality-floor` boundary, carrying the floor's `criticality` and the floor boundary in `criticality_from`; `graph.jsonl` has no such records. Any SQL client can ask "which artifacts implement anything under lib:Media?":

```sql
SELECT a.path, a.symbol FROM concept_artifacts a
JOIN is_a_closure c ON c.sub = a.concept
JOIN nodes h ON h.id = c.super WHERE h.curie = 'lib:Media';
```

`gloss mcp` serves the same graph to agents over the Model Context Protocol.
